## Context

- **Queue topology**: per-stage queues (CLAUDE.md:63; evidence_layer_plan.md:280 — no parse stage) vs priority classes `on_demand > refresh > seed` (research_flows.md:88,174), never reconciled. Redis priority only works via emulated sub-queues (`queue_order_strategy`, `priority_steps`). Options: stage × priority queues, or dedicated on_demand workers.
- **Chain shape for the Batch API** (from "Extraction execution").
- Defaultables: sync SQLAlchemy + `def` routes; Redis result backend (chords need one); tenacity for HTTP + Celery autoretry for transient errors; DLQ = `on_failure` → `failed_tasks` table + replay command (Redis has no native DLQ); one in-flight research per entity; A2 dedup by normalized query; `acks_late` + prefetch 1; empty rate-limit bucket → `retry(countdown)`; Playwright on its own queue/image; time limits; single Beat instance, timezone, scheduler persistence.
- Context7 for Celery API specifics (CLAUDE.md documentation rules).
- **From "Schema conventions"** (2026-11-05; conventions in evidence_layer_plan.md §4; no on-demand research per decisions.md §15): the A2 priority queue and A2 dedup are gone. The `failed_tasks` table, its columns and retention are this ticket's. An ingest item's `failed` result now covers resolution errors only; later failures belong to the entity's research.
- **From "Claim identity"** (2026-11-06; notes in evidence_layer_plan.md §4 `claims`): ambiguous claim names are retried automatically when identity data changes, and all claims are re-resolved after a resolution rules change; when and on which queue these run is this ticket's.
- **From "Edge lifecycle: ending, retraction and staleness"** (2026-11-07; notes in evidence_layer_plan.md §4 `edges`): moved here: concurrency of publishing (a lock per brand or a single publish queue). Also needed in Beat: a daily sweep that marks edges `unconfirmed` after 18 months without confirmation, and a daily sweep that expires pending deals after 18 months without completion.
- **Fact checked 2026-11-08** (Celery docs via Context7, "Backends and Brokers", docs.celeryq.dev/en/stable/getting-started/backends-and-brokers/; raised when the developer asked whether Redis is needed): Celery lists three stable brokers, RabbitMQ, Redis and Amazon SQS; Zookeeper, Kafka and Google Cloud Pub/Sub are experimental. Using SQLAlchemy (a database such as Postgres) as the broker was removed in Celery 4.0; SQLAlchemy remains supported only as a result backend. Monitoring and remote control (Flower, `celery inspect`) work on RabbitMQ and Redis, not SQS. No decision was taken; the stack still lists Celery + Redis (CLAUDE.md).
- **From "Category storage and recompute"** (2026-11-07; tables `entity_categories` and `entity_pe_owner_periods` in evidence_layer_plan.md §4): each affected brand is recomputed in its own Celery task, queued in chunks after an owner-kind or edge change; a nightly Beat task recomputes every stored brand and compares (the drift check).
- **From "Rosters, portfolio pages and the registry"** (2026-11-12; notes in evidence_layer_plan.md "Registry crawler"): a registry pass runs as tasks across many domains, each domain's requests in order (crawl delay, token bucket); Playwright visits for `render: browser` pages and for the one honest retry on a challenge need a browser pool or their own queue; one `source_runs` row per pass covers every required page plus the new releases.
- **From "Extraction execution"** (2026-11-15): extraction is synchronous (DeepSeek has no batch API), one task per document read (windows inside it); bulk work (first seeding pass, version re-reads, the daily sweep of `unreadable` reads for 7 days) waits for DeepSeek's off-peak hours (prices double 01:00–04:00 and 06:00–10:00 UTC on weekdays); single new documents go at once; requests have a 15-minute timeout and answers took a median 13 seconds in testing; concurrency against DeepSeek is this ticket's.
- **From "Extraction prompt rules"** (2026-11-15; evidence_layer_plan.md Stage 3 step 3 and §4 `api_incidents`): during a DeepSeek outage (three "down" attempts on one document: no answer, the timeout, or HTTP 500/502/503/504) single new documents go straight to the fallback and bulk work waits for DeepSeek or the developer's command, without being marked `unreadable`; a 402 or 401 from DeepSeek pauses every DeepSeek read. Scheduled jobs: a tiny DeepSeek test request every 5 minutes while an outage is open, a free DeepSeek balance check every 5 minutes while paused for a 402, and a free OpenRouter key-balance check every 5 minutes while the fallback is out of funds; each resumes the waiting reads. A 429 slows the sending rate and retries on DeepSeek (DeepSeek allows 2,500 concurrent requests on `deepseek-flash`). Waiting reads must survive worker restarts, and a manual resume keeps the off-peak hold for bulk work unless run with "now".
- **From "Form ADV and IRS exempt-org ingestion"** (2026-11-15; evidence_layer_plan.md "Form ADV connector"): tasks for the monthly adviser load (two files, about 24,000 rows, about 12,900 loaded), the one-time FOIA archive load (about 1.1 GB zipped, the largest CSV about 770 MB), and the IAPD PDF parser (large firms' PDFs run to hundreds of pages, Leonard Green's 509 pages and 23 MB; pdfplumber ran out of memory on it, pypdf page by page worked). SEC fair access: at most 10 requests a second.
- **From "BDC discovery and Schedule of Investments parsing"** (2026-11-16; section "BDC connector and Schedule parser" in evidence_layer_plan.md §5): BDC fetches share the SEC's 10 requests a second with EDGAR full-text search and Form ADV (one sec.gov bucket); primary documents run up to 63 MB uncompressed (median about 10 MB), so parse tasks are large; each Schedule's outcome (clean, partial, failed) is reported as a whole.
- **From chains "Website stack and hosting"** (2026-11-18): scheduled site builds: one after the overnight run, only if every job finished without crashing (single-source failures don't count; a skipped build alerts the developer); one at 2 pm and one at 8 pm in the developer's time zone, only if something published since the last build. Each calls the Cloudflare Pages deploy hook.
