# Citation verification rules

Type: grilling
Status: open
Blocked by: 16, 17  (Claim value schemas and values over time; Claim producers and the claims door)
Map: [engine](../map.md)

## Question

What exactly does `verify_citations` normalize and check, and which sanity checks run where?

## Context

- **Normalization spec** (only edge cases are listed: build_roadmap.md:69; conformance-tests SKILL:15–16, which still owes "the developer's own edge-case list"): case sensitivity, NFKC, smart quotes/dashes/nbsp/ellipsis mapping, PDF hyphenation and ligatures, table-cell separators, min/max quote length, whether "…" elisions are allowed, mapping normalized offsets back to the original.
- **Sanity checks** (evidence_layer_plan.md:184–186): "doc mentions the subject alias" — exact or fuzzy; object too? "event_date plausible" — by what rule? "numbers in value appear in the quote" — formats, "in thousands", parenthesized negatives, basis points.
- **Do structured claims go through verify?** Form 5500, NPPES, selector-made claims (see "Claim producers…").
- **Where the BDC numeric cross-check sits**: bdc-parser SKILL:14 and build_roadmap.md:117 say the claim is never emitted; ADR 0002:16 and research_flows.md:133 say rejected; evidence_layer_plan.md:186 makes it a verify-stage sanity check (`sanity_check_failed`). "Withheld filing" has no status/reason in the settled vocabulary (claim status pending|accepted|rejected|retracted + rejection_reason).
- **From "Claim producers and the claims door"** (2026-11-05; summary in evidence_layer_plan.md "Producers and the door"): answered here: every producer's claims go through `verify_citations`. Quote rules per document kind are settled (bulk row = the whole data line; JSON = code-rendered field lines). Identity record values are checked in the door with this ticket's normalization, as found and before storage normalization. A code producer's per-record failure raises an alert. Where the BDC numeric cross-check sits stays here.
- **From "Predicate semantics"** (2026-11-05; role table in evidence_layer_plan.md §4 `claims`): a new sanity check: a resolved claim whose subject or object type the role table doesn't allow is rejected with `sanity_check_failed`.
- **From "Entity lifecycle"** (2026-11-06; notes in evidence_layer_plan.md §4 `entities`): `renamed_from` adds a check: `value.former_name` must appear in the quote.
- **From "Claim identity"** (2026-11-06; notes in evidence_layer_plan.md §4 `claims`): checks this adds: each name as written must appear word for word in the document (whether also inside the quote is this ticket's); a vague phrase passed off as a name ("the company") needs a rule here; after resolution both entity types must fit the role table (misfit → `sanity_check_failed`). Offsets are `quote_start`/`quote_end` into the stored `raw_text`; mapping a normalized match back is this ticket's.
- **From "ExtractedClaim and the extraction result envelope"** (2026-11-06): `verbatim_quote` length rules, which dates are plausible, and whether a press release's dateline can supply `event_date` are this ticket's. Item-level checks in the envelope (a name as written missing from the document, an unknown document label, a bad date) drop the item before it becomes a claim.
- **From "Claim value schemas"** (2026-11-06; schemas in evidence_layer_plan.md §4 `claims`): numbers to check against quotes: `stake_pct`; BDC amounts, which are stored in full units with `scale` (1, 1,000, 1,000,000) from the table's "(in thousands)" header; rates as percent numbers. `stake_type` (`majority|minority`) is set only when the document uses the word, which needs a check here.
- **From "Owner kind: storage, evidence and the PE-firm test"** (2026-11-07; ADR 0001 amended; table in evidence_layer_plan.md §4 `owner_kind_evidence`): `owner_descriptions` quotes pass `verify_citations` like claims, and the describing phrase must appear in its quote.
- **From "What 'checked' means and coverage states"** (2026-11-07; ADR 0001 amended; tables `document_reads` and `source_runs` in evidence_layer_plan.md §4): a document whose claims all fail `verify_citations` gets the read outcome `claims_rejected`, which keeps its source run incomplete (a misquote doesn't show the document holds no evidence).
- **From "Document storage, fetch log and last-confirmed"** (2026-11-07; notes in evidence_layer_plan.md §4 `documents` and `fetches`): `verify_citations` searches only a document's `raw_text`; parsed tables and locator records are child documents with their own `raw_text`. Stored text keeps all visible text, PDFs carry a page marker at each page break, and each document records its `text_extractor_version`; normalization rules are this ticket's.
- **From "Task: Compare extraction models on audit documents"** (2026-11-13; results in research/extraction-model-comparison.md): some quotes failed only on characters such as an en dash ("– operating under the brands of"); the test normalized whitespace and quote marks but not dashes. How dashes and similar characters are normalized decides whether such near misses count.
- **From the extraction precision check** (2026-11-14; research/extraction-model-comparison.md): all six claims judged wrong had quotes that passed the exact-match check but didn't name the claim's subject or object (a brands-page heading quoted for five brands; a lender group's stake credited to one unnamed member). A rule that a claim's names appear in its quote, allowing the page's own owner as the unnamed object of a portfolio listing, would have caught all six. Two renames also lacked the former name in the quote, which the existing rename rule already rejects.
- **From the DeepSeek prompt iteration** (2026-11-14; research/extraction-model-comparison.md "DeepSeek prompt iteration"; prompt in research/extraction-test-prompt-v5.md): most failed quotes came from the test's HTML-to-text step, not the model: a space inserted wherever HTML splits text into elements ("100 %", "$ 1.473 billion", "Werhahn Group .") and SEC page footers ("76 Table of Contents") mid-sentence. The models quoted the document as it reads. Set aside, DeepSeek's exact-quote rate goes from 96% to 99.3%, GLM's from 94% to 99.2%, Mistral's from 90% to 97%. Two consequences: the "Document storage" text extractor must not put separators between inline elements and must deal with filing page footers (an implementation detail of "keep all visible text", or a ruling on stripping footers); and this ticket's normalization may need to ignore spacing around numbers and punctuation. A repair call (send the passage around the best match, ask for an exact copy) fixed 12 of 15 failed quotes.
- **From the clean-text confirmation** (2026-11-14; research/extraction-model-comparison.md): with block-aware extraction (line breaks only around block elements, nothing between inline pieces), DeepSeek v5 read the clean text of 157 documents and 615 of 615 quotes matched it exactly. The model and the check must see the same cleanly extracted text; page-footer stripping made no difference in this set.
