## Question

How are the sponsor/rollup registry, portfolio pages and DSO/rollup location rosters stored, crawled, diffed and turned into documents and claims?

- **From "Claim producers and the claims door"** (2026-11-05; summary in evidence_layer_plan.md "Producers and the door"): settled there: portfolio pages go to the LLM; `selector` producers only read long uniform lists (store locators, location rosters); store-locator JSON endpoints are allowed when robots.txt permits them and they feed the public locator page; a JSON record is one document. Still this ticket's: the selector config schema, its revision number (which is the selector's `producer_version`), the selector shape check (expected fields, roughly the usual item count, run before anything is written), and whether an HTML roster page is one document or one per item (the item's text must appear in the page's text either way).
- **From "Predicate semantics"** (2026-11-05; role table in evidence_layer_plan.md §4 `claims`): a roster or store-locator item yields an `operated_by` claim (location → the company that runs it) when the page states the operator, and `location_brands` rows from the brand names in its identity record. Portfolio pages yield `owned_by`.
- **From chains-and-brands "Brand and chain model"** (2026-11-06): launch needs the registry and sponsor portfolio pages only. Store-locator selectors are for the store-map follow-up (stores without operators). DSO and rollup location rosters are parked with local businesses.
- **From "Entity lifecycle"** (2026-11-06; notes in evidence_layer_plan.md §4 `entities`): in the store-map follow-up, a store missing from its brand's locator sets the location's `status = closed` (the diff rule is this ticket's with "Edge lifecycle").
- **From "What 'checked' means and coverage states"** (2026-11-07; ADR 0001 amended; tables `document_reads` and `source_runs` in evidence_layer_plan.md §4): the registry's `documented|reported|inferred` vocabulary stays inside the registry and never reaches a card (the registry is a crawl list, never evidence). Sponsor pages are a shared source: a pass counts when every page on the list was fetched and read, and a page that keeps failing leaves the list only by a code change after the operator report flags it.
- **From "Document storage, fetch log and last-confirmed"** (2026-11-07; notes in evidence_layer_plan.md §4 `documents` and `fetches`): a sponsor page's versions are its document rows per extracted text; an unchanged page costs nothing, and a changed page is re-read whole. A store-locator response is a parent and each store record a recurring child (endpoint plus store id).
- **From "Edge lifecycle: ending, retraction and staleness"** (2026-11-07; notes in evidence_layer_plan.md §4 `edges`): a sponsor page that drops a company stops confirming the hop but never ends it (ownership never ends by absence). Stores and roster locations, in the store-map follow-up or local businesses, close after missing from two complete crawls in a row.
- **From "Source independence and syndication"** (2026-11-08; ADR 0002 amended; notes in evidence_layer_plan.md §4 `documents`): a sponsor's portfolio page speaks for the sponsor (the entity holding its domain), and a rollup's roster for the rollup; for a hop between them they are one ownership group, so one source. Verification needs a source outside the group (an outlet, an adviser, the seller, a filing).
- **From "Press and EDGAR full-text connectors"** (2026-11-08; scrape etiquette in CLAUDE.md; press-connector note in evidence_layer_plan.md): a matched wire release is fetched from the issuer's own site, so the registry should hold each sponsor's and brand's newsroom (or press page) URL, and the connector looks there or in the site's sitemap for a matching title and date.

## Answer

Resolved 2026-11-12 in a grilling session over two days (two rounds with several revisions and three measurements, recorded under Comments).

- **Split:** selector work moved to new ticket "Selector producers: store locators and rosters", whose status-only selector is needed for launch.
- **Registry:** one YAML file per organization in the repo, loaded into Postgres by `registry sync`; the developer approves an entry by committing it. Entries: every company or investment firm on a listed brand's chain with a portfolio page, newsroom or about page, plus each listed brand's newsroom and about page. Fields: `name`, `identifiers` (lookup only), `domains`, `pages` (`url`, `role` = `portfolio|newsroom|about`, `render`, `paging_param`, `detail_links`, `required`, `status_selector`), `research` (never read by code). Launch target: every owner on a listed brand's chain that publishes a portfolio page or newsroom has an entry; an operator gap report tracks it.
- **Speakers:** each entry goes through the door as an operator intake item; its domains become `domain` identifier rows sourced by that item; Form ADV writes `domain` rows from `Website Address`, skipping social media; crd/cik never written from the registry.
- **Extraction:** nothing from the registry reaches the prompt. HTML text keeps hidden elements and writes `alt`, link `title` and `aria-label` in place (new extractor version). Status only in markup or a server-side filter is read by a status-only selector (about 27 of 73 pages). Listed means current unless marked former in text; a mixed list gives no claim for unmarked items. A name missing from any page means nothing (a current-only rule was considered and dropped: it would apply to 2 of 73 pages).
- **Crawl:** detail pages by a `detail_links` pattern, one level deep, each its own document re-fetched with conditional requests; paging by parameter, capped at 50; no sitemaps for portfolio pages; `render: browser` for JavaScript pages. Newsrooms: the whole archive on the first crawl, then only new releases; each release fetched once as `press_release`; every unread release read by the LLM.
- **Confirmation (corrects "Document storage" and "Edge lifecycle"):** `company_site` documents confirm whenever seen again with the company on them; every other source type confirms only as of the claim's own date (event date, else `published_on`, else first fetch). The 18-month window stays, with its reason written into ADR 0001.
- **Challenges:** one retry per page per pass in the bot's own unmodified browser, no clicks, up to a fixed wait; blocked unless it clears by itself; a hard block or a site's request stops all fetching from the domain; robots.txt first. Measured from a home IP: 90 of 93 PE firm sites readable this way (Warburg Pincus only through the browser); Neuberger Berman, Partners Group and Anchorage closed. Walled-at-research pages get `required: false`. The developer explored getting around every block (research on stealth tools, CAPTCHA services and HandsOn); deferred as map fog "Walled sites, later". Claude won't answer "verify you are human" checks or build solver hand-offs.
- **Tables:** `registry_entries`, `registry_pages`, `crawl_targets`, `site_access`, `site_access_changes`; `entity_identifiers.ingest_item_id` for `domain` rows; one `source_runs` row per registry pass.
- **Dropped:** the "sponsor registry crawl index".
- Docs: evidence_layer_plan.md (§4 `entity_identifiers`, `documents` text rule and last-confirmed, `fetches`, `edges` last_confirmed_on, five new tables; "Registry crawler" section); ADR 0001 (why 18 months, what confirms); CLAUDE.md scrape etiquette (the honest retry); GLOSSARY "Registry"; research_flows.md, build_roadmap.md, pre-launch-seeding.md; registry-research skill rewritten; conformance-tests skill. Engine map fog "Walled sites, later". Research: [portfolio-page-survey](../research/portfolio-page-survey.md), [bot-protection-workarounds](../research/bot-protection-workarounds.md), [portfolio-wall-survey](../research/portfolio-wall-survey.md), [portfolio-page-types](../research/portfolio-page-types.md).
