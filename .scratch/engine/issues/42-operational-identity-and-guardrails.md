Type: grilling

## Question

What is the product's public identity for crawling, what are the budget caps and guardrail values, and where do operational alerts go?

## Context

- **Rate limiting**: per-registrable-domain Redis token bucket, default rate/burst, per-domain overrides (SEC), Lua script or the `limits` library (evidence_layer_plan.md:284), shared by httpx and Playwright.

Google Places is likely $0 for version 1 (no map; brand lookup doesn't need it).

- **From "Press and EDGAR full-text connectors"** (2026-11-08; scrape etiquette in CLAUDE.md; press-connector note in evidence_layer_plan.md): the bot needs the project's own name in its user agent (no contact detail), the same name in Playwright, no proxies or CAPTCHA services, and a per-site stop when a site asks; a cap on documents fetched per brand per run is also needed.

The spend guardrails must budget for whole-filing reads, together with the per-name hit cap (up to 100 hits per name on a first run). Also: the SEC asks bots to declare a contact in the user agent; whether to use a project mailbox there (never the developer's personal email) is this ticket's.
- **From "Rosters, portfolio pages and the registry"** (2026-11-12; notes in evidence_layer_plan.md "Registry crawler"): values needed: the newsroom first-crawl read cap (rough size 150 entries × 300 archived releases ≈ 45,000 LLM reads, then only new releases); the challenge retry's wait (30 s suggested); the paging cap (50 pages). Also apply to Cloudflare's verified bot program, whose requirements were read 2026-11-11 (research/bot-protection-workarounds.md §6): a Web Bot Auth signature (an Ed25519 key published as a JWKS at `/.well-known/http-message-signatures-directory`, signed headers on every request) or a published IP list, robots.txt obeyed, reasonable rates, applied for through Cloudflare's dashboard form; verified status can be revoked for every bot an organization runs if one evades blocks. Web Bot Auth needs the bot's public name and domain from this ticket (tests used `EvidenceEngineBot/0.1`, not a decision).

- **From "Extraction prompt rules"** (2026-11-15; evidence_layer_plan.md Stage 3 step 3 and §4 `api_incidents`): extraction alerts when an incident opens (DeepSeek down, its balance empty, or its key rejected), when the fallback runs out of funds (OpenRouter 402 or 403 for credits or the key limit), and daily while an incident is open. - **From "BDC discovery and Schedule of Investments parsing"** (2026-11-16; section "BDC connector and Schedule parser" in evidence_layer_plan.md §5): the BDC per-Schedule failure-rate threshold (above it the Schedule is failed and withheld) is a setting whose value is this ticket's; a rounding tolerance for the fair-value total follows each filer's stated `decimals`.
- **From chains "Research: Where PE owns consumer brands"** (2026-11-16): research workers repeatedly slipped on redirects: following a redirect to a new host before reading that host's robots.txt, following one into a disallowed path, and fetching inside a crawl-delay; one retried plain 403 responses in a browser. CLAUDE.md doesn't say how the bot handles redirects or whether a 403 refusal (as opposed to a challenge page) gets the one browser retry. Proposed for this ticket: a redirect target is checked against its own host's robots.txt and crawl-delay before it is followed, and a plain 403 is a refusal, never retried in the browser.
- **From chains "Research: Audits of five product industries" and "Research: Screen of five more industries"** (2026-11-17): two of seven research workers each sent one request before reading the target host's robots.txt (a homepage fetched in the same command as robots.txt; a robots.txt redirect followed to another host's homepage), the same slip as earlier runs. Proposed for the engine and for research tooling: one shared fetcher that refuses any request to a host whose robots.txt it hasn't read and parsed, follows no redirect itself, and logs every refusal; every connector and research worker goes through it. Also recorded: a research worker whose direct request the session's permission check refused reached the same host through a browser's own button; research workers now stop and report on any refused request.
- **From chains "Research: Follow-up audits of four industries"** (2026-11-17): a third one-request slip came from a browser retry that followed a redirect to an unread host by itself, so the proposed shared fetcher must also intercept redirects inside a browser (Playwright request routing) before they are followed, not only in curl.
- **From chains "Source-link submissions"** (2026-11-18): rate limits for the "Report a mistake" form (per connection, per brand, per day) and its invisible bot check (a hidden field); no third-party CAPTCHA.
- **From "Retrieval fan-out, tracked entities and refresh cadence"** (2026-11-20; evidence_layer_plan.md §5 Stage 2): (1) research climbs owners up to a **hop cap** against loops from bad data; its value is this ticket's. (2) **Full-text search noise:** EDGAR full-text search on a big brand name returns hundreds to thousands of hits (Aspen Dental 2,095, Natrol 1,543, MB2 Dental 1,408), mostly lenders' schedules, landlords' tenant lists and mortgage-pool prospectuses. Ticket 70 reads every hit whole, so most of that spend goes to noise, and the newest-first 100-hit cap can push older real filings out. Budget it here, or reopen the read-everything ruling with the developer. (3) Failed runs retry daily for up to 7 days, which adds to fetch load.

An operational alert when a firm classed private equity passes $25bn in registered funds. Where the alert goes is this ticket's.
